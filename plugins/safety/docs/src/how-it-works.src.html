claude-setup · safety guards

Guards that judge what a command would do, not what it says

Claude Code can delete a folder, push over a branch or post a file to a stranger in one line. These guards are hooks that read each tool call before it runs, work out its real effect, and stop the ones that can't be undone. They're code, not instructions, so they don't depend on the model choosing to obey them. Every block tells Claude a safe way to do the job instead, so the work carries on.

01 · The shape

Every tool call passes its guards before it runs

Each guard is a Claude Code hook: a short script Claude Code runs on a tool call before it goes ahead (PreToolUse) or after it comes back (PostToolUse). It reads the call as JSON and answers with an exit code: 0 lets it through, 2 blocks it, and whatever it wrote to stderr goes back to Claude. A shell command passes all five shell guards at once, and any one of them can stop it. Pick a box to see what it stops and the exact message Claude gets.

02 · Inside command-guard

It reads a command the way the shell will run it

A shell lets you spell one command a hundred ways, so command-guard doesn't search the text for bad words. It takes the command apart as bash would, works out every file it would touch, then asks one question: does every target stay inside the places deletes are allowed? Pick a command and replay it.

Two rules keep it usable. When it can't parse something, it lets it through, because a guard that blocks everything it doesn't understand gets switched off within a week. When it has parsed a destructive command but can't show the target is contained, it blocks. Tool caches like node_modules, .venv and __pycache__ can be deleted anywhere, because a package manager rebuilds them. Generic names like build and dist deliberately can't.

03 · What the agent sees

A block is an instruction, not a dead end

Claude reads the block message and decides what to do next, so every guard writes it for Claude, and every one ends with a safe way to get the same job done. Claude usually takes it and carries on, which is why the guards can stay on all day without anyone switching them off.

BLOCKED by git-guard [reset-hard]: `git reset --hard` throws away every uncommitted change in the working tree and index.
DO THIS INSTEAD: commit or stash the work first (`git stash push -u -m 'before cleanup'`), then reset; or use `git reset --keep`, which refuses to overwrite uncommitted changes.

Some blocks have a way through. Someone at the keyboard can let one command through by prefixing it with CLAUDE_GUARD_OVERRIDE='why', and the reason is logged. Be clear about what that is: Claude writes the commands, so it can add the prefix too. It's a speed bump that makes the agent stop and give a reason on the record. Switch to unattended and see what changes.

Override accepted when attended

Recursive deletes outside the session folder · sending data to a host not on the list · writing a secret file from the shell · destructive git · opening a port

Hard floors: never, whoever asks

Protected folders · the agent's own settings, hooks and instructions · disk, partition and power commands · download-and-run · deleting backups or force-pushing over remote history

What it looked like on my own agents

49 overrides in three weeks, every one written by the agent itself

All 49 were in sessions I was watching. None were in headless runs, where they're refused. 39 of the command guard's 45 gave the identical reason, on a delete whose target the guard couldn't see, so the agent's own explanation was the only record of what went. A speed bump, not a lock.

The catch, and why it's still there

A safe alternative also shows a determined agent where the line is

Redwood Research found in May 2026 that retrying with detailed feedback from a monitor is easy for an attacker to exploit. The explanation stays because most blocked agents are honest and stuck, and it's what keeps them working. What an adversarial agent can't argue past are the hard floors and the headless runs, and what catches one that keeps probing is a monitor watching the whole session.

04 · Can the agent switch it off?

Hooks in your settings can be switched off. Managed ones can't

A plugin's hooks live in settings files, and an agent that wants a way round has several. Each row below is a real way out and the thing in this repo that closes it.

The plugin install

One command, no admin rights

Catches the agent in normal use, which is nearly all of it. An agent determined to get round it can start a child session without it.

The managed install (macOS)

Root-owned copies the session can't touch

managed/install.sh puts the guards under /Library/Application Support/ClaudeCode, owned by root. Both copies run and a call needs both to allow it, so tightening the plugin works at once and loosening needs a reinstall. It needs your password, so you run it, never Claude.

Proving it's on: the canary

Every launch route, tested from outside

managed/canary.sh starts a short headless claude -p on each route an agent could take: plain, with every hook switched off, with only project settings, and with a fake python3 and BASH_ENV. Each asks for one harmless command the git guard blocks. A route passes only when the managed ledger records the block.

05 · When a guard breaks

An unsure guard lets the command through. A damaged one is refused, and a crash is logged

This is the part most hook setups get wrong. Claude Code blocks on exit 2, or an explicit deny in JSON. Any other exit code doesn't block, and nor does a hook that times out. So a guard that crashes protects nothing and says nothing, and a guard caught half-written by an editor or an update can exit 0 and wave everything through, looking exactly like a normal allow.

So it fails both ways on purpose. A guard unsure about a command allows it. A missing or damaged guard means nothing is checking, so the call is refused: the one place it fails closed, at the cost of reading the last 200 bytes of the file. The gap that's left is a guard that hangs, which is one more reason the guards are short scripts using only the standard library.

Why the break log matters

It caught a bug in the wrapper itself

On 27 Sep, 28 breaks landed in one minute. A guard path given relative to the caller's folder stopped resolving once the wrapper moved to /, so the guard never ran. It was a test run, and it was fixed that afternoon. Without the log, those 28 would have looked exactly like 28 allows.

06 · Coming back in

Text from the web is data, and the guard says so

Everything Claude fetches was written by someone else, and some of it is written for the model, not for you. The strongest tell is text a person can't see. Unicode has a block of "tag" characters that render as nothing but read as ordinary letters to a model. Here's a recipe review with an instruction hidden in it.

It runs after the fetch, so it never blocks: there's nothing left to stop. Invisible characters are stripped before phrases are matched, because a zero-width space inside "ignore previous instructions" beats a matcher while the model still reads the phrase. And if a page does talk Claude into sending your key somewhere, egress-guard is waiting on the way out.

07 · How we know

Tested like an attacker, then run on real agents

A guard can fail two ways. A hole lets damage through. An over-block stops ordinary work, and that one is worse in practice, because the owner switches the guard off. The tests count both. No test runs a command: guards get the command as text and return a verdict, and every path points into a throwaway folder.

test-kit/probe.py

95 disguises, 0 holes

Reshaped commands across 20 classes: quoting, variable tricks, wrappers, nested shells, heredocs, one-liners, encoding, path tricks, environment steering. 14 are ordinary commands that must stay allowed. It reports every HOLE and OVER-BLOCK.

test-kit/replay.py

Your own week, through old and new

Before you change a guard, it replays the commands you actually ran through both versions and prints counts only: what got stricter and what got looser. No command or path is shown, because your history holds secrets.

CI

Every push, macOS and Linux

The cases, the wrapper tests and the probe run on every push. The probe step fails the build unless it ends on 0 HOLES | 0 OVER-BLOCKS.

08 · Your machine

Install it, and know where it sits

  1. Install

    Add the marketplace, then the plugin

    /plugin marketplace add marliechorgan/claude-setup
/plugin install safety@claude-setup

    Restart Claude Code so the hooks load. From then on, a blocked command shows its message in the transcript, and Claude takes the suggested route.

  2. Configure

    Name your protected folders and the hosts you send data to

    Optional: the defaults already protect your home folder, ~/.ssh, ~/.gnupg, ~/.aws, ~/.config, ~/Documents, ~/Desktop, ~/Library and ~/.claude, and allow sending data to no host at all.

    mkdir -p ~/.config/claude-safety
curl -fsSL https://raw.githubusercontent.com/marliechorgan/claude-setup/main/plugins/safety/config.example.json -o ~/.config/claude-safety/config.json

    Add only hosts you genuinely send data to. Think before adding a broad one: allowing api.github.com also allows posting any file to a gist. Edit it yourself, in your own editor; Claude can't.

  3. Unattended

    Be stricter on scheduled and headless runs

    CLAUDE_SAFETY_UNATTENDED=1 claude -p "…"
  4. Lock it

    Optional on macOS: the managed install, then the canary

    git clone https://github.com/marliechorgan/claude-setup
cd claude-setup/plugins/safety/managed
./install.sh --dry-run
./install.sh
./canary.sh

    Run it in your own terminal: it asks for your password, and it refuses to run inside a Claude session. ./install.sh --verify checks it any time.

Where it sits: the layers, weakest at the bottom

Above this repoA monitor watching the whole session reads intent across many steps: the script the agent writes and then runs, the agent that keeps probing. Code can't judge either.
This repoManaged install and canary. On whatever flags an agent starts with, and proven on every launch route.
This repoGuards that judge the effect. Deterministic, about 0.15 s a command, a safe alternative on every block.
Built inAuto mode's classifier is a model: a good second opinion that isn't deterministic.
Built inAllow and deny lists match text. Use them to cut prompts, not as the boundary.
What it costs

Claude Code runs matching hooks in parallel, so a shell command waits for the slowest guard plus the wrapper: 129 to 224 ms, about 150 ms typically, over 48 runs on an M-series Mac with the machine busy on 2 Oct 2026. Run one after another, the five would take about half a second. Writes and edits pay for config-guard alone, about 130 ms. To drop a guard you don't need, remove it from hooks/hooks.json.

What it can't do
  • A script file the agent writes and then runs is judged by how it's run, not what's inside it.
  • Text built at run time with sed or awk and piped into sh is only partly visible.
  • Publishing tools aren't judged: git push (other than a force-push), npm publish, twine upload, and gh posting while you're watching.
  • AppleScript telling Terminal to run something is outside Claude's tools. Don't grant Claude automation rights over Terminal.
  • A guard that hangs past its timeout lets the call through. A short secret in a short URL can still leave.
  • An agent that can write and run code can in principle do anything your account can. Guards raise the cost and catch the common and the accidental; the layer above is for the rest.
